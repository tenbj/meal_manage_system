# 需求识别报告：减脂双餐后台服务层

## 1. 需求背景

当前业务原型指向的是一个内部运营后台，用来支撑“午餐 + 晚餐”的减脂餐服务。服务不是单纯卖餐，而是围绕客户体重目标、忌口偏好、每日反馈、出餐克重、标签配送、服务总结与复购沟通形成持续管理。

从现有离线原型看，业务已经有比较明确的日常运营闭环：

- 新客建档，记录身体基础信息、目标体重、运动量、减脂速度、配送地址、忌口、过敏、不喜欢的菜。
- 为客户开通 6 天体验服务或 28 天正式服务，并跟踪服务状态、剩余天数和付款状态。
- 维护菜品库，包括菜品分类、食材、熟重热量、营养字段、数据出处、蒜味、搭配冲突和今日可用性。
- 每日生成午餐、晚餐食谱，并允许给客户做单独替换。
- 按活跃客户生成每日出餐表，计算每道菜克重、总克重、总热量，并做确认、暂停和特殊餐盒标记。
- 录入客户每日反馈，反馈影响第二天克重建议。
- 生成餐盒标签、配送清单和服务结束总结海报，用于履约和复购沟通。

因此，这个需求的本质不是“做一个菜单管理工具”，而是把减脂餐服务中容易依赖人工记忆、表格复制和微信群沟通的环节结构化，降低出错率，提高每日交付效率，并沉淀可复购的客户服务记录。

## 2. 需求来源

当前可用来源：

- `README.md`：说明原型边界、建议验收路径、未来九类数据表。
- `05_减脂双餐后台服务层原型.html`：离线工作台入口。

来源性质判断：

- 这是“已成型原型 + 样例数据”带来的需求倒推，不是直接来自真实用户访谈或线上数据。
- 需求动机更接近创始人/运营侧对业务流程的抽象，属于强业务假设，仍需要用真实操作人员和历史订单验证。
- 原型已经体现的字段和流程可视为一版业务共识，但营养算法、履约规则、权限边界、数据合规和异常场景仍是待验证部分。

## 3. 目标用户与角色

| 角色 | 目标 | 当前可能行为 | 主要痛点 |
|---|---|---|---|
| 运营管理员 | 管理客户、订单、每日任务和服务进度 | 用表格、聊天记录、手工备注维护 | 信息分散，容易漏掉即将结束服务、反馈未处理、特殊客户 |
| 配餐/食谱负责人 | 制定当天午晚餐食谱，处理不可用菜和客户替换 | 根据经验选菜，再人工核对忌口 | 忌口、过敏、菜品冲突、热量出处难统一检查 |
| 出餐执行人员 | 按客户生成每餐克重并确认出餐 | 手工查客户、抄克重、临时沟通调整 | 克重错、特殊餐盒漏做、暂停客户仍出餐 |
| 客服/跟进人员 | 收集客户反馈并推动第二天调整 | 在微信或表格里记录体重、饱腹感、不喜欢的菜 | 反馈难转化成可执行建议，连续反馈不易观察 |
| 配送协调人员 | 生成标签和配送清单 | 复制客户地址和餐品内容 | 标签信息不一致，配送备注漏掉，午晚餐地址/时间易混 |
| 业务负责人 | 观察服务质量、完成率、复购机会 | 靠人工复盘 | 难判断履约质量，服务结束时缺少可复用的转化素材 |
| 客户 | 收到符合自己目标和限制的减脂餐，并感到被持续跟进 | 通过反馈表达饿、撑、吃不完、不喜欢 | 反馈如果没有被系统承接，会降低信任和复购意愿 |

## 4. 核心场景

### 场景 A：新客户开通服务

- 触发：客户购买体验服务或正式服务。
- 任务：建立客户档案，记录身体信息、目标、忌口、过敏、配送地址，并开服务订单。
- 当前替代方式：表格建档、聊天记录补充、手工算服务结束日期。
- 期望结果：客户进入服务中状态，后续每日出餐自动纳入。
- 失败点：信息漏填、服务周期算错、客户过敏和忌口没有进入出餐提醒。

### 场景 B：每日生成午晚餐食谱

- 触发：每日出餐前，需要确定当天午餐和晚餐菜单。
- 任务：按荤、海鲜、素、主食生成组合，核对热量出处、蒜味数量、食材丰富度、菜品可用性和搭配冲突。
- 当前替代方式：人工挑菜后再逐项检查。
- 期望结果：当天食谱可被出餐表、通知文字和替换流程复用。
- 失败点：不可用菜仍被选中，同一餐蒜味过重，食材冲突未发现，客户忌口未被提前识别。

### 场景 C：客户单独替换

- 触发：客户忌口、过敏、不喜欢某道菜，或当天食谱与客户限制冲突。
- 任务：针对某客户、某餐次、某原菜品记录替换菜和原因。
- 当前替代方式：微信群或手工备注提醒厨房。
- 期望结果：重新生成出餐表时自动带入替换，并标记是否确认。
- 失败点：替换只存在聊天记录里，出餐人员看不到；替换未确认就进入履约。

### 场景 D：每日出餐和克重确认

- 触发：食谱确定后，要为每个活跃客户生成午餐、晚餐出餐表。
- 任务：系统按客户计划和餐品热量生成每道菜克重，出餐人员可微调、确认、暂停。
- 当前替代方式：手工复制客户名单和克重。
- 期望结果：每个客户每餐都有明确菜品、克重、热量、忌口提醒和状态。
- 失败点：客户暂停但仍出餐，特殊餐盒漏做，手工调整被重新生成覆盖。

### 场景 E：客户反馈影响第二天调整

- 触发：客户吃完午晚餐后反馈体重、是否吃完、饱腹感、身体状态和不喜欢的菜。
- 任务：记录反馈并产出明日克重建议。
- 当前替代方式：客服阅读聊天后凭经验提醒配餐。
- 期望结果：偏饿、偏撑、没吃完、不喜欢的菜能转化成第二天调整信号。
- 失败点：反馈没有被处理，客户新偏好没有沉淀进档案，调整依据不可追溯。

### 场景 F：标签、配送与服务结束复盘

- 触发：每日出餐确认后生成标签和配送清单；服务结束后生成总结海报。
- 任务：复制或导出标签、配送文字、总结图。
- 当前替代方式：人工复制客户姓名、地址、菜品和文案。
- 期望结果：履约信息一致，结束服务时有可复用的复购沟通素材。
- 失败点：配送清单遗漏特殊备注，海报数据不准确，客户隐私被不当暴露。

## 5. 当前问题与痛点

### 症状

- 客户信息、订单周期、忌口过敏、菜品热量、反馈和配送地址可能分散在多个地方。
- 每日午晚餐涉及多个客户、多个餐次、多个菜品和克重，人工复制成本高。
- 特殊规则多：过敏、忌口、不喜欢、不可用菜、蒜味、搭配冲突、暂停服务、即将结束服务。
- 客户反馈如果只停留在聊天记录里，很难稳定影响第二天出餐。
- 服务结束时需要总结客户成果，但体重、反馈、坚持率等数据容易临时拼凑。

### 可能根因

- 业务对象没有结构化：客户、订单、菜品、食谱、出餐、反馈、配送、海报之间缺少统一数据关系。
- 每日履约链路太依赖人脑记忆和临时沟通。
- 反馈和配餐之间没有闭环机制。
- 运营结果没有沉淀成可复盘、可复购的资料。
- 当前原型是本地 `localStorage`，还不能支持多人协作、真实数据和权限控制。

| 编号 | 需求陈述 |

| R1 | 作为运营管理员，当客户开始体验或正式服务时，我需要建立客户档案并开通服务订单，以便系统知道哪些客户应进入每日出餐。 |

| R7 | 作为客服/跟进人员，当客户反馈体重、饱腹感、是否吃完和不喜欢的菜时，我需要记录并生成第二天建议，以便把客户感受转化为配餐调整。 |
| R8 | 作为配送协调人员，当出餐表确认后，我需要生成餐盒标签和配送清单，以便减少午餐、晚餐配送信息错误。 |
| R9 | 作为业务负责人，当服务即将结束或已结束时，我需要生成客户阶段总结和海报，以便做复盘、复购和客户沟通。 |
| R10 | 作为业务负责人，当系统接入真实数据时，我需要数据库、服务端、权限和审计能力，以便多人安全协作并保护客户隐私。 |

## 7. 需求优先级

### Must Have：MVP 必须具备

| 需求 | 优先级 | 理由 |
|---|---|---|
| 客户档案与体重记录 | 高 | 所有后续计算、忌口提醒、配送和复盘都依赖客户基础数据。 |
| 服务订单与周期状态 | 高 | 决定哪些客户进入每日出餐，以及何时提醒结束和复购。 |
| 菜品库管理 | 高 | 食谱、克重、热量、标签内容都依赖菜品结构化数据。 |
| 每日午晚餐食谱 | 高 | 是出餐执行的上游核心。 |
| 客户单独替换 | 高 | 直接影响过敏、忌口和服务体验，出错成本高。 |
| 每日出餐表与克重确认 | 高 | 是厨房/出餐执行的主工作台。 |
| 客户反馈录入与明日建议 | 高 | 形成“服务型减脂餐”的核心差异化闭环。 |
| 标签与配送清单 | 高 | 直接影响履约准确性。 |
| 今日看板 | 高 | 用来聚合每日待办和风险项，提升运营效率。 |

### Should Have：上线早期应具备

| 需求 | 优先级 | 理由 |
|---|---|---|
| 真实数据库和服务端 API | 中高 | 原型数据只在浏览器本地，不能支撑真实业务。 |
| 多角色权限 | 中高 | 客户隐私、菜品维护、出餐确认、海报导出应分权。 |
| 操作日志和变更记录 | 中高 | 克重、替换、删除、重新生成都需要可追溯。 |
| 数据导入导出 | 中 | 便于从旧表格迁移，也便于日常备份。 |
| 异常处理机制 | 中 | 包括暂停服务、补餐、改地址、改餐次、退款/取消。 |
| 通知文字模板 | 中 | 原型已有复制通知文字，真实业务可增强模板管理。 |

### Could Have：后续可扩展

| 需求 | 优先级 | 理由 |
|---|---|---|
| 库存和采购联动 | 中 | 菜品不可用可能来自库存，但 MVP 可先人工标记。 |
| 配送路线优化 | 中 | 当前只需生成清单，路线规划可后置。 |
| 客户端小程序/表单反馈 | 中 | 可减少客服录入，但需要先验证反馈字段。 |
| 自动复购提醒和销售跟进 | 中 | 服务总结海报可先手动使用。 |
| 营养师审核流 | 中 | 如未来强调专业背书，可加入审核和处方边界。 |

### Won't Have：当前阶段暂不纳入

- 不做完整外卖交易平台。
- 不做在线支付闭环，当前只记录付款状态。
- 不做医学诊断、治疗建议或疾病管理。
- 不做复杂库存、采购、供应商结算。
- 不做面向客户的完整 App，除非后续验证客服录入成本过高。

## 8. 范围边界

### 本期应包含

- 内部后台工作台。
- 客户档案、体重记录、订单周期。
- 菜品库和基础营养/热量字段。
- 午餐、晚餐食谱生成与人工调整。
- 客户单独替换。
- 每日出餐表、克重调整、确认、暂停。
- 客户反馈录入和明日调整建议。
- 标签和配送清单生成。
- 服务总结海报生成和记录。
- 今日待办看板。

### 本期不包含

- 真实客户自助下单。
- 支付、退款和财务对账系统。
- 自动采购、库存消耗和成本核算。
- 自动配送调度。
- 医疗合规问诊或治疗方案。
- 与微信/短信/小程序的自动消息发送，除非作为后续扩展。

### 关键约束

- 真实业务上线必须接数据库，不能继续依赖本地浏览器存储。
- 客户电话、地址、体重、身体反馈、过敏信息都属于敏感信息，需要权限和隐私规则。
- 营养和热量算法需要专业校验，不能只依赖样例代码。
- 多人同时操作时，需要冲突处理和日志。
- 重新生成食谱或出餐表会覆盖人工调整，真实产品中必须给出确认、历史版本或恢复机制。

## 9. 假设与待验证问题

### 当前默认假设

- 业务主打每日午餐 + 晚餐双餐服务。
- 主要服务周期是 6 天体验服务和 28 天正式服务。
- 每个活跃客户默认每天需要午餐和晚餐，除非暂停。
- 客户反馈至少包括体重、午晚餐是否吃完、饱腹感、不喜欢的菜和身体状态。
- 克重建议可以根据基础代谢、运动量、减脂速度和昨日反馈做初步计算。
- 标签与配送清单主要供内部复制使用，不一定马上对接打印机或配送系统。
- 服务总结海报用于复盘和复购沟通，而非公开宣传素材。

### 必须确认

- 真实运营中有哪些角色？一个人兼多职，还是运营、配餐、出餐、配送、客服分工明确？
- 双餐服务是否所有客户都固定午餐 + 晚餐？是否存在只订午餐、只订晚餐、临时改餐、停餐、补餐？
- 客户忌口、过敏、不喜欢、宗教/生活习惯限制是否需要分级？哪些属于绝对不可触碰？
- 克重/热量计算公式由谁背书？是否需要营养师审核或人工确认阈值？
- 菜品热量出处是否有统一标准？熟重、生重、供应商数据如何管理？
- 今日不可用菜品的原因是什么？库存不足、原料质量、厨房产能，还是临时停售？
- 出餐表确认后还能不能改？谁有权限改？改动是否需要记录原因？
- 配送地址是否午餐和晚餐可能不同？是否需要配送时间窗、骑手、路线、楼层备注？
- 服务结束海报是否允许展示体重变化？是否需要客户授权或脱敏？
- 真实上线最先要解决的是“出餐不出错”，还是“服务反馈闭环”，还是“复购转化”？

### 建议确认

- 体验服务转正式服务的关键节点和话术是否需要系统提醒。
- 即将结束服务提前几天提醒最合适。
- 客户连续几天偏饿、偏撑、未吃完时是否触发人工复盘。
- 菜品搭配规则除蒜味和食材冲突外，还有哪些业务经验规则。
- 标签内容是否需要标准格式、品牌信息、营养信息或食用提醒。
- 总结海报是否需要多个模板、品牌视觉、二维码或顾问署名。

### 可后置确认

- 是否需要库存、采购和成本核算。
- 是否需要客户自助反馈入口。
- 是否需要打印机、配送平台、微信通知等外部集成。
- 是否需要经营报表，例如服务完成率、复购率、出餐异常率、反馈覆盖率。

## 10. 验证方式与成功标准

### 最轻验证方式

1. 原型走查
   - 参与者：运营、配餐负责人、出餐执行、客服/跟进、配送协调。
   - 方式：按 README 建议验收路径走完整流程。
   - 目标：确认字段是否够用、流程顺序是否符合真实工作。

2. 小规模人工试运行
   - 范围：选 10-20 个脱敏客户，连续跑 3 个真实出餐日。
   - 方式：一边使用原型，一边记录哪些环节仍要靠微信或表格补充。
   - 目标：验证是否真的减少遗漏和重复录入。

3. 历史数据回放
   - 范围：拿 1-2 周历史订单、反馈、出餐和配送记录。
   - 方式：录入原型，看是否能还原当时的出餐结果和服务总结。
   - 目标：验证数据模型是否覆盖真实业务。

4. 风险场景演练
   - 场景：过敏客户、暂停服务、临时改地址、菜品不可用、客户偏饿、客户未吃完、服务即将结束。
   - 目标：确认系统能把异常明确暴露出来，而不是隐藏在备注里。

### 成功标准

- 每日生成食谱和出餐表所需时间明显低于当前人工方式。
- 忌口、过敏、不可用菜、特殊替换的漏处理次数下降。
- 活跃客户每日反馈覆盖率可被看见，并能转化为第二天建议。
- 标签和配送清单信息与出餐表一致，减少重复复制。
- 运营能在首页看板看到当天最需要处理的事项。
- 服务结束时可在 5 分钟内生成可用于客户沟通的总结素材。
- 试运行后，真实工作人员愿意继续使用，而不是回到原表格。

## 11. 建议下一步

1. 先做一次 60-90 分钟业务流程走查，把“真实每日工作顺序”画出来。
2. 用 3 个真实但脱敏的客户样本验证客户档案字段，重点看忌口、过敏、地址、反馈是否够用。
3. 让出餐人员用原型生成一次真实午餐和晚餐出餐表，记录所有仍需口头沟通的内容。
4. 请配餐负责人确认热量、克重、餐次比例和反馈调整规则，标出哪些是必须人工审核。
5. 确认 MVP 第一目标：履约准确率、服务跟进效率、复购转化，三者只能先选一个作为主目标。
6. 若上述验证通过，再交给 `$002-prd-writer` 输出 PRD，重点补页面字段、权限、异常流程、数据表和验收标准。
