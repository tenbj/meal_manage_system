# 减脂双餐后台管理系统 v2

商家首页为备餐工作台、客户与订单、我的菜品、店铺设置。默认准备明天，按照「主菜单＋按需添加备用菜 → 添加已登记客户、确认忌口 → 打印标签」操作。今天分装直接显示大字昵称、逐菜克重，可逐盒确认完成。后端使用 MySQL 持久化。

备用菜可逐道添加，数量和荤素分类不限，也可暂不添加，不默认计入每盒；忌口冲突可点选适用备用菜。取消菜单沿用；主菜单与同日另一餐、前一天或后一天任一餐存在同菜时提示并阻止确认。新客户登记和用餐安排分开；身体资料直接展开且选填，登记和购买包餐均不会自动添加用餐人。配送必须填写地址，自提需明确选择。

客户与订单按客户去重统计累计订餐、包餐、仅单次人数，提供序号、筛选及每期餐卡账本。每次续订新增一期，原购买次数不可覆盖；安排时优先使用有效期内最早购买、尚有可用餐次的包餐卡，再使用有效单次订单，否则建立本餐单次订单。余额 = 购买 + 手动调整 − 已完成盒数 − 取消仍扣次数。待出餐盒数单独预留，防止跨日期超排。取消可由商家选择返还或仍扣，原因必填；取消、恢复、完成以及手动补扣均保留流水，服务器保护原购买记录和已有流水。取消一盒不会使其他已核对餐盒停止分装。

标签突出昵称、逐道菜的克重、总热量、配送地址或自提信息。菜单或名单变化后需重新确认；已经打印且受影响的标签提示重打。纸张容纳不下内容时阻止打印并提示调整尺寸，避免裁掉地址或重量。每道菜的成品热量完整后才能打印标签。未来日期不能提前确认出餐完成。

新版使用 `/api/merchant` 和 `merchant_workspace` 表，第一次读取时从旧系统导入客户、订单、菜品及出餐记录，原表保留。此后新版数据以新表为准，旧 `/api/state`、AI 写入接口和原版页面的写入不会同步到新版，暂勿混用。旧字段和原表未删除，旧反馈与海报仍保留在原系统；新版聚焦出餐流程。

热量外部来源限定为薄荷健康，已按官方公开文档实现 `X-Api-Key`、食物搜索和详情接口。店铺设置提供连接入口，真实查询成功才保存密钥到被 Git 忽略的 `.runtime/boohee.json`；也支持服务端环境变量 `BOOHEE_API_KEY`。未提供用户授权时明确显示未连接，不伪造数据。搜索先查已保存菜品，无匹配才调用薄荷；可明确选择继续查薄荷。确认分类及熟重/即食口径后，服务器重新读详情并持久化，重复编码不重复入库。液体或无有效 kcal 数据的条目不导入；配料不完整仍触发忌口核对。薄荷原始热量只读，手动录入保留来源依据。文档：[请求规范与食物接口](https://ai.boohee.com/docs/)。

定菜单时先在选菜弹窗中搜索本地菜库；找不到可直接搜索薄荷或手动新建。保存新菜会入库并回到原选择，自动勾选新菜，同时保留已有勾选和基准克重。关闭录入可返回继续选菜，不会提前改写本餐菜单。手工录入必须有每 100 g 成品热量、熟重/即食口径和数值依据；缺失热量的旧菜需补全才能使用。前端与服务端均拒绝将未验证热量用于新菜单、备用菜和出餐，不再允许跳过热量检查打印；原历史记录保留。

连接验证会去除粘贴内容首尾空白，并拒绝含星号的脱敏 Key。网络、超时、证书、HTTP 和薄荷业务错误分别显示，业务错误展示经过密钥脱敏的上游原因与错误码。薄荷可能在 HTTP 200 中返回非零业务错误码，不能仅凭 HTTP 状态判断成功。已有连接可在设置内重新检测，无需重新输入 Key；更换验证失败不会覆盖旧 Key。只有真实食物搜索成功且返回菜品列表结构才保存连接。

`node scripts/reset-merchant-catalog.js` 只读预览旧菜品清理范围；显式加 `--apply` 才执行一次清理。清理前保存本机忽略目录 `tmp/` 中的快照，清空可选菜库与相关菜单引用，保留历史餐盒快照、必要历史菜品引用与原餐次余额；清理标记防止重复误删新添加的菜品。此操作不清空客户与订单，也不影响原版旧数据表。

打印使用浏览器打印（可存为 PDF），默认纸张 50 × 70 mm，可在店铺设置调整。确认打印不扣餐次；出餐完成或商家选择取消仍扣时扣次；历史完成记录保留菜品数据快照。修改未完成餐盒会提示重打标签。

## 自动配餐与基准克重

客户可填写性别、年龄（周岁）、身高（cm）、当前体重（kg）。成年客户资料齐全时，使用 Mifflin–St Jeor 静息代谢估算公式：`10×kg + 6.25×cm − 5×年龄 + 性别常数`（男 +5、女 −161），单餐目标为估算值的 36%，午晚餐分别使用该目标。这是商家配餐规则，不是全天饮食需求。公式来源：https://pubmed.ncbi.nlm.nih.gov/2305711/ 。

资料不全时不分性别统一以 500 kcal 为单餐目标，400–600 kcal 为可接受范围；旧版 1400 / 1600 设置不再参与计算。未成年人不套用成人代谢公式。

主食合计分配目标热量的 1/3，其余菜合计分配 2/3。每组先按菜单基准克重计算基准热量，再用「组目标热量 ÷ 组基准热量」同比缩放该组所有菜的克重，取整到 1 g。这样同组保持商家设定的搭配比例，多个主食不会重复领取 1/3 热量。缺少有效成品热量、热量为零，或菜单缺少主食/菜组时，保留基准量并明确提示不能自动配餐。标签实际热量永远按最终克重重新求和。

菜单基准值由商家录入，不是客户个体建议：历史导入主食 120 g、其余 150 g，新菜初值 150 g。身体资料、热量密度、菜单或备用菜变更后，未完成的自动餐盒重新计算并使旧标签失效；手动餐盒固定全部克重，可恢复自动。已完成餐盒的目标、菜品、热量和客户快照不变。`scripts/check-merchant-portions.cjs` 验证新增流程，全部写入使用隔离数据。

## 技术栈与目录

- Node.js + Express
- MySQL / mysql2
- 商家工作台：`public/index.html` 与 `public/assets/merchant*`
- 原始原型归档：`prototype-source/`

## 常用命令

```bash
npm install
npm run db:setup
npm run db:seed
npm start
```

与原版同时验收时，可在 PowerShell 使用 `$env:PORT='3201'; npm start`，访问 `http://localhost:3201`。端口由环境变量决定，默认仍为 3200。

验证使用 `npm test` 和 `npm run smoke`。受限环境无法启动测试子进程时，可使用 `node --test --test-isolation=none tests/*.test.js`。浏览器测试应通过网络拦截使用隔离数据，避免向真实业务数据写入测试客户。

启动后访问：

```text
http://localhost:3200
```

健康检查：

```text
http://localhost:3200/api/health
```

更多部署细节见 [docs/deployment.md](docs/deployment.md)。

原版外部脚本接口见 [AI 功能写入 API](docs/skill-data-api.md)，这些接口只影响旧数据表，尚未迁移到新版出餐工作台。

当前端到端检查脚本为 `scripts/check-merchant-operations.cjs`；原 `check-merchant-ui.cjs` 与 `check-merchant-portions.cjs` 均调用该统一验收。使用已安装的 Playwright（可用 `PLAYWRIGHT_MODULE` 指定模块路径）及本机 Chromium，`MERCHANT_URL` 默认指向 `http://localhost:3201`。脚本只读取真实数据，全部修改请求被拦截到内存测试夹具；截图和打印视图尺寸验收结果保存在忽略目录 `tmp/`。真实授权调用需配置用户 API Key 后另行验证；自动测试中的薄荷结果均为隔离夹具。

选菜专项验收：`node scripts/check-menu-picker.cjs`（同样支持 `PLAYWRIGHT_MODULE` / `MERCHANT_URL`）。覆盖录入中断返回、必填热量、原勾选保留、薄荷添加后自动选入、本地复用、连接失败重试与移动端布局。该脚本所有业务写入及薄荷调用均使用隔离数据。

选菜弹窗和我的菜品均提供主食、荤菜、素菜、海鲜分类按钮及数量，选菜条目和菜单行显示类别；我的菜品按分类分组展示。分类筛选可与名称搜索叠加，切换分类保留已有勾选。

服务端校验薄荷来源、餐次调整和取消流水时按 JSON 实际内容比较，不依赖对象字段顺序；MySQL JSON 存储重排字段不会再将新导入的薄荷菜误判为改写。菜单、名单和配餐签名也忽略对象字段顺序，兼容已有签名，真实数值或菜品次序改变仍使确认与标签失效。测试存储夹具模拟 MySQL 字段重排，覆盖导入后立即保存菜单及真正修改热量仍被拒绝。
